# Headless 纯 API 模式运行说明

## VPS 实时观看

远程直播默认开启，读取 `data/remote_live.json`，使用已配置的 SSH 免密登录。
缺失配置、认证或远端服务不可用时输出具体原因并跳过，不阻塞 bot 进桌。
关闭时增加 `--no-remote-live`；本机 `--no-web` 与远程直播开关互相独立。
独立服务、免重启上传和一键部署说明见 [remote_live/README.md](../../pf_entertainment/remote_live/README.md)。

## 启动默认值

2026-11-11 起，实战用的策略环境变量全部写进了代码默认值，裸命令

```bash
nohup caffeinate -i .venv/bin/python -m pf_intercept.headless --bb 10000 --buyin-bb 100 --profit-lock-bb 140 --max-auto-rebuy 0 > pf_intercept/logs/headless_console.log 2>&1 &
```

等价于显式写出 `DECISION_ENGINE=cfr PF_BUCKET_ML=lgbm PF_POSTFLOP_PROFIT_EXPAND_V1=1
REALTIME_CFR_TIMEOUT_SEC=10`（桶 ML 为 2026-11-11 重建版，见 docs/range_v2_bucket_ml.md），入口还会自动等价设置
`PYTHONUNBUFFERED=1`。要做对照实验时再显式覆盖（例如 `PF_BUCKET_ML=off`），`session_config.env`
只记录显式设置的值，`session_config.resolved` 记录实际生效值。

## PID 管理与优雅停止

从项目目录运行下面的命令，停止本项目的 headless 实例：

```bash
.venv/bin/python -m pf_intercept.headless --stop
```

启动参数无需改变。终端、`nohup caffeinate -i` 和 PyCharm 的模块启动均由 bot 自己维护
`pf_intercept/logs/headless.pid`，记录实际 Python 进程 PID，不是 shell 或 caffeinate 的 PID。
`pf_intercept/logs/headless.lock` 保存进程启动时间与完整命令并持有独占文件锁，阻止同一项目重复启动。
本进程管理使用 macOS/Linux 的文件锁。

`--stop` 不登录游戏，也不需要设置启动时的策略环境变量。它核验 PID、锁状态和进程身份后发送
`SIGINT`，请求打完当前手后离桌；命令返回仅表示请求已发送，不表示退出完成。
原有离桌确认最多等待 45 秒的行为保持不变，之后关闭连接并完成日志、奖励请求等收尾。
若在选线期间请求停止，会在探测返回后退出；登录、重连与恢复等待可由停止信号打断，不再请求进桌。

正常退出、启动失败时自动删除 PID 文件；强制终止可能留下 PID，但文件锁由操作系统释放，
停止命令不会仅凭残留 PID 发信号，下次启动会覆盖它。`.lock` 文件会保留，这是正常行为；
**不要在 bot 运行时删除它**。此功能只管理更新代码后启动的实例，旧版进程仍需用原停止方式。

程序本身追加写入 `pf_intercept/logs/headless.log`。
`pf_intercept/logs/headless_stdout.log` 只有使用 shell 重定向时才会写入，包含控制台输出；
PyCharm 不依赖该重定向，仍然会生成程序日志及 PID 文件。

## 意外离桌恢复与耗时诊断

通过 `--bb` 自动匹配的现金桌，收到成功的 `LeaveRoomRSP` 时，如果仍有剩余筹码，且不是
主动停止、盈利锁仓、破产换桌或校准积压暂停，会先刷新余额，再用本次启动的盲注和买入金额
重新匹配。已使用的自动续入次数和次数上限均保持不变。破产仍遵守原续入限制。
优雅停止会先禁止重进；已经在大厅时直接收尾，不再向旧房间等待离桌确认。

Web 收到离桌确认后立即清空旧牌桌，并显示大厅状态；重新进桌后以新快照展示。
服务器已推进到下一行动（包括系统弃牌）的旧决策会丢弃，防止队列积压后补发过期下注。

G5 每手仍更新真实行动统计，但只为本手玩家生成保存快照，完整模型由后台线程原子替换，
慢盘期间合并尚未开始的保存请求。退出会等待最后一次保存完成。JSON 字段与版本保持兼容，
只去掉持久化文件中占空间的缩进。`g5_model_saved` 的 `mode=background_checkpoint` 和
`elapsed_ms` 表示实际后台保存完成及耗时；失败写 `g5_model_save_failed`。
`headless.log` 对超过 500 ms 的处理或排队记录 `handler / queue_ms / handle_ms / backlog`，
用于区分决策、结算持久化和消息积压。

## 断线自动重连

`--bb` 对局模式在心跳超时、连接被断开或发送失败后保持进程和 Web 运行，自动重新连接。
重试间隔依次为 1、2、4、8、16、30 秒，之后保持 30 秒；从原线路开始，失败时轮换登录返回的
可用线路。启动命令无需增加参数。Web 显示「自动重连中／恢复牌桌中」，不会把旧快照显示成正常连接。

登录后按客户端协议等待 `UserLocationRSP`：

- `roomid > 0`：发送不带买入金额的 `EnterRoomREQ`，恢复原桌、筹码和当前行动。
- 明确返回大厅：清除旧桌状态，按原 `--bb` 和 `--buyin-bb` 匹配；已知破产、主动停止或
  校准积压暂停的状态不会因此被重新买入。
- 位置推送或房间快照超时：重建连接后再次确认，不凭旧房间号或超时猜测可以重新买入。

重连复用同一份 bot、资金基线、模型、已用续入次数、次数上限和奖励服务；不重新开一轮统计。
旧连接中尚未发送的行动／续入／重进请求会被取消，不跨连接补发；当前牌局由新快照恢复。
断线期间暂停奖励轮询，已有领取请求仍记录返回结果；恢复资金状态后继续，不清空已领取和待核对记录。

登录被明确拒绝、收到退出登录推送（包括其他设备登录）或停服推送时停止重连，记录原因，避免反复抢占账号。
`--stop` 能打断重连退避、连接和恢复等待。若仍在连通的牌桌，继续按优雅离桌流程退出；
已断线时直接收尾，不为退出而重新买入。

重连日志使用 `[RECONNECT]`；心跳超时同时记录距离最后收包的时间。自动重连无法还原断线期间
未收到的完整行动历史，现有恢复流程会禁用该手无法完整重放的 G5 旁路。

## 游戏服务自动绕过代理

启动命令无需设置 `NO_PROXY` 或 `no_proxy`。bot 恢复会话时，从登录响应中保存的
`servers[].server_host` 和 `servers[].http_host` 提取主机名/IP，去掉协议、端口和路径，
合并进当前进程的 `NO_PROXY` 与 `no_proxy`，保留用户已有条目。HTTP 地址为空时，
也加入该会话实际使用的默认 HTTP 主机。名单随登录返回的服务器列表变化，不写死游戏域名。

此步骤在选线 `/ping` 之前执行，覆盖全部备用线路的 WSS 和 HTTP 请求，包括自动领取奖励。
直接使用 `HeadlessSession` 建立连接时也会执行，重试时可补充更新后的地址。
不会修改系统代理设置、shell 配置或启动命令；macOS 的有效系统代理地址会保留到进程内，
避免新增 `no_proxy` 后其他地址意外失去代理配置。

`headless.log` 的 `[NETWORK]` 记录本次游戏服务名单，不记录凭证。
连接/登录失败及程序启动异常也写入该日志，即使控制台被重定向至 `/dev/null` 仍可排查。
更新代码不影响已运行进程，下一次启动生效。

## 对手历史数据查询

Headless 的 `/player/gameData` 使用当前会话的 HTTP 凭证、所选线路、渠道及客户端版本，
与游戏连接、奖励领取保持一致；不会回退到旧 `data/auth_token.txt`。
MITM 代理模式仍保留读取捕获 token 文件的方式。

- `code=-2` 按鉴权失败处理：记录并提醒一次，暂停使用同一凭证查询；有效凭证更新后可恢复。
- 只有 `code=0` 且明确返回 `play_times=0`，才提醒“暂无历史统计”，不据此判断新号、小号或激进倾向。
- 超时、请求失败和无效数据不记为“已查询”。冷却 30 秒后，在下一手开始时重试仍在本手的玩家，
  同一玩家的请求不并发重复，成功结果本次会话只取一次。
- 修改磁盘上的 headless 会话文件不会热更新已运行进程；新凭证由下次启动读取。

## 自动领取奖励

`python -m pf_intercept.headless` 默认开启发展基金、每日任务、每周任务和相应活跃度奖励领取。
原启动命令无需增加参数；临时关闭全部自动领取可追加 `--no-auto-rewards`。
协会经营、挑战任务、购买月卡、消费道具和上报任务进度不在本功能范围内。

## 触发与领取流程

- 启动：WSS 登录成功并拿到首次钱包余额基线后，后台检查基金与日／周任务。
- 发展基金：收到 `pb.NoticeBRC.type=10082`（`GAME_REBATE_SETTLE`）立即唤醒检查。
  先查询 `/activity/rebateStatus`，有可领取状态才调用 `/activity/rebate`。
  后一个接口按客户端行为视为具有领取副作用，不能拿它当只读探测接口。
- 阶段切换：使用服务器时间，在 **UTC+8 的 07:00、19:00** 唤醒基金检查，
  跨阶段后的 10 分钟内每 30 秒复查；服务器仍在结算时也每 30 秒复查。
  日常每 5 分钟补查，覆盖断线、漏推送等情况；推送无需等待轮询周期。
- 任务：收到 `pb.NoticeBRC.type=10030`（`TASK_REFRESH`）合并短时间内的重复通知，刷新 `/task/list`。
  通知本身不代表任务已完成。仅领取列表中 `status=2` 的每日／每周任务，
  使用任务实例 `id`，不使用静态 `task_id`。
- 月卡专属任务：先读取 `/player/payInfo`，只在月卡有效期晚于服务器当前时间时领取。
  资格未知时跳过专属项，普通任务照常处理。
- 任务奖励：`/task/recReward` 指定符合条件的 `id_arr`，`all=false`，避免隐式领取未核验项目。
  随后刷新列表，再领取已达到门槛且未领取的 `/task/recPointReward` 活跃度奖励。
  每次领取后重新查询状态，允许本次任务奖励解锁的宝箱在同一次检查中领取。

## 并发、失败和关闭

HTTP 调用在独立后台任务的线程中执行，不占用 WSS 接收循环、心跳或策略处理锁。
同一会话的领取请求串行处理，避免重复推送产生并发领取。
请求超时后不直接重发领取请求，下一轮先重新读取服务器状态。
这不能保证网络故障下的“恰好一次”：若服务器已发奖但响应丢失，到账金额可能无法确认，日志会标记 `claim_uncertain`。

HTTP 返回 `code=-2` 表示鉴权失效，本次会话停止自动领取并记录提示，对局连接继续。
领取使用当前 WSS 会话对应的 `authorization`、渠道、客户端版本和线路 HTTP 地址，
不读取可能过期的独立 `auth_token.txt`，也不会自动登录并替换正在使用的账号会话。
更新本地会话凭证后，下次启动才使用新凭证。

关闭时停止新增领取请求，并等待正在执行的请求返回或超时，把领取结果记完再关闭。
测试使用模拟 HTTP/WSS，不会替账号领取真实奖励。

## 日志与资金看板

- 常规日志：`pf_intercept/logs/headless.log` 中的 `[REWARDS]`。
- 结构化记录：`pf_intercept/logs/rewards.jsonl`。
  包含时间、UID、本次奖励服务 `run_id`、事件、任务／宝箱 ID、奖励筹码及道具；不记录密码和 token。
  `claimed` 是收到成功响应，`claim_uncertain` 是领取结果无法确认，`auth_failed` 是鉴权失效。
- 资金看板新增“本次领取奖励筹码”。“本次对局盈亏”及后续采样／手牌累计点扣除已确认到账的奖励。
  钱包余额仍显示服务器实际值。领取中以及领取后的余额尚未刷新时显示“余额刷新中”，
  避免交错返回的旧余额被误当成对局盈亏。
- 出现到账金额不明的领取时，看板显示“奖励待核对”，避免把未知奖励混入对局盈亏；
  已确认的奖励总数仍保留在日志和看板中。

本功能不会启动 bot；代码更新在下一次启动时生效。
