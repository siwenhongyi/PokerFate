# Headless 纯 API 模式运行说明

## VPS 实时观看

远程直播默认开启，读取 `data/remote_live.json`，使用已配置的 SSH 免密登录。
缺失配置、认证或远端服务不可用时输出具体原因并跳过，不阻塞 bot 进桌。
关闭时增加 `--no-remote-live`；本机 `--no-web` 与远程直播开关互相独立。
独立服务、免重启上传和一键部署说明见 [remote_live/README.md](../../pf_entertainment/remote_live/README.md)。

## 启动默认值

2026-11-11 起，实战用的策略环境变量全部写进了代码默认值，裸命令

```bash
nohup caffeinate -i .venv/bin/python -m pf_intercept.headless --bb 10000 --buyin-bb 100 --profit-lock-bb 140 --max-auto-rebuy 0 > pf_intercept/logs/headless_console.log 2>&1 &
```

等价于显式写出 `DECISION_ENGINE=cfr PF_BUCKET_ML=lgbm PF_POSTFLOP_PROFIT_EXPAND_V1=1
REALTIME_CFR_TIMEOUT_SEC=10`（桶 ML 为 2026-11-11 重建版，见 docs/range_v2_bucket_ml.md），入口还会自动等价设置
`PYTHONUNBUFFERED=1`。要做对照实验时再显式覆盖（例如 `PF_BUCKET_ML=off`），`session_config.env`
只记录显式设置的值，`session_config.resolved` 记录实际生效值。

## PID 管理与优雅停止

从项目目录运行下面的命令，停止本项目的 headless 实例：

```bash
.venv/bin/python -m pf_intercept.headless --stop
```

启动参数无需改变。终端、`nohup caffeinate -i` 和 PyCharm 的模块启动均由 bot 自己维护
`pf_intercept/logs/headless.pid`，记录实际 Python 进程 PID，不是 shell 或 caffeinate 的 PID。
`pf_intercept/logs/headless.lock` 保存进程启动时间与完整命令并持有独占文件锁，阻止同一项目重复启动。
本进程管理使用 macOS/Linux 的文件锁。

`--stop` 不登录游戏，也不需要设置启动时的策略环境变量。它核验 PID、锁状态和进程身份后发送
`SIGINT`，请求打完当前手后离桌；命令返回仅表示请求已发送，不表示退出完成。
原有离桌确认最多等待 45 秒的行为保持不变，之后关闭连接并完成日志、奖励请求等收尾。
若在选线期间请求停止，会在探测返回后退出；登录、重连与恢复等待可由停止信号打断，不再请求进桌。

正常退出、启动失败时自动删除 PID 文件；强制终止可能留下 PID，但文件锁由操作系统释放，
停止命令不会仅凭残留 PID 发信号，下次启动会覆盖它。`.lock` 文件会保留，这是正常行为；
**不要在 bot 运行时删除它**。此功能只管理更新代码后启动的实例，旧版进程仍需用原停止方式。

程序本身追加写入 `pf_intercept/logs/headless.log`。
`pf_intercept/logs/headless_stdout.log` 只有使用 shell 重定向时才会写入，包含控制台输出；
PyCharm 不依赖该重定向，仍然会生成程序日志及 PID 文件。

## 意外离桌恢复与耗时诊断

通过 `--bb` 自动匹配的现金桌，收到成功的 `LeaveRoomRSP` 时，如果仍有剩余筹码，且不是
主动停止、盈利锁仓、破产换桌或校准积压暂停，会先刷新余额，再用本次启动的盲注和买入金额
重新匹配；带多少筹码受净亏损上限约束（见下）。
优雅停止会先禁止重进；已经在大厅时直接收尾，不再向旧房间等待离桌确认。

## 净亏损上限

一次启动只有一个止损数：净亏损不超过 (1 + `--max-auto-rebuy`) 个 100BB 买入，按 `--bb` 的大盲折成筹码
（`--bb 20000 --max-auto-rebuy 2` 就是 600 万）。净亏损 = 服务端每手结算的累计，赢到的自动抵掉。

所有把筹码带上桌的动作都先过这一条：**已亏的 + 桌上的 + 要带的 ≤ 上限**。

- 桌上补码：补到不超过 100BB 的最大一档，且不超过上限的余量。
- 破产买入：余量放得下 100BB 就买 100BB，否则买余量容得下的最大一档。
- 换桌、异常离桌后的重新买入：同上。正在亏的时候，带回去的不会比离桌时的筹码多出上限以外的部分。
- 盈利锁仓重进不检查：它拿下桌的比带回去的多。

档位是客户端买入滑块的档位（20–30BB 每 1BB 一档，40BB 起每 10BB 一档；买入、破产买入、补码是同一个滑块）。
连最小一档 20BB 都放不下时，本次启动到此为止：停在大厅，不再买入、匹配、补码，推送
`净亏损到上限 · 已停止`；奖励领取照常，重启后恢复。

不再单独数破产买入的次数，盈利锁仓也不再给上限 +1。

## 桌上补码

一手结束时桌上筹码低于 70BB（且没输光）就在桌上补码，不离桌：发客户端菜单「补充筹码」同款的
`pb.SetRebyREQ(reby_chips=加多少)`，服务端在下一手发牌前把筹码加到桌上并广播
`pb.RebyBRC(type="topup")`，到账后发一条 `桌上补码` 通知（补了多少、桌上筹码、本次启动盈亏）。

- 加多少：补到不超过 100BB 的最大一档（客户端滑块的档位：20–30BB 每 1BB 一档，40BB 起每 10BB 一档）。
  例：65BB 补 30BB，45BB 补 50BB。
- 上限：净亏损上限（见上）。余量不够最小一档就不再补，照旧打下去；`--max-auto-rebuy 0` 时
  只有本次启动是赚的才补得上。
- 盈利锁仓、选桌离桌、破产换桌进行中，以及优雅停止之后，不补码。
- 服务端拒绝、或两手之后仍没到账，隔 30 手再试。
- 补码是买入，不计入本次启动盈亏（盈亏只累计服务端每手结算）。
- `--topup-below-bb N` 改阈值，`0` 关闭。

Web 收到离桌确认后立即清空旧牌桌，并显示大厅状态；重新进桌后以新快照展示。
服务器已推进到下一行动（包括系统弃牌）的旧决策会丢弃，防止队列积压后补发过期下注。

G5 每手仍更新真实行动统计，但只为本手玩家生成保存快照，完整模型由后台线程原子替换，
慢盘期间合并尚未开始的保存请求。退出会等待最后一次保存完成。JSON 字段与版本保持兼容，
只去掉持久化文件中占空间的缩进。`g5_model_saved` 的 `mode=background_checkpoint` 和
`elapsed_ms` 表示实际后台保存完成及耗时；失败写 `g5_model_save_failed`。
`headless.log` 对超过 500 ms 的处理或排队记录 `handler / queue_ms / handle_ms / backlog`，
用于区分决策、结算持久化和消息积压。

## 断线自动重连

`--bb` 对局模式在心跳超时、连接被断开或发送失败后保持进程和 Web 运行，自动重新连接。
重试间隔依次为 1、2、4、8、16、30 秒，之后保持 30 秒；从原线路开始，失败时轮换登录返回的
可用线路。启动命令无需增加参数。Web 显示「自动重连中／恢复牌桌中」，不会把旧快照显示成正常连接。

登录后按客户端协议等待 `UserLocationRSP`：

- `roomid > 0`：发送不带买入金额的 `EnterRoomREQ`，恢复原桌、筹码和当前行动。
- 明确返回大厅：清除旧桌状态，按原 `--bb` 和 `--buyin-bb` 匹配；已知破产、主动停止或
  校准积压暂停的状态不会因此被重新买入。
- 位置推送或房间快照超时：重建连接后再次确认，不凭旧房间号或超时猜测可以重新买入。

重连复用同一份 bot、资金基线、模型、净亏损上限和奖励服务；不重新开一轮统计。
旧连接中尚未发送的行动／续入／重进请求会被取消，不跨连接补发；当前牌局由新快照恢复。
断线期间暂停奖励轮询，已有领取请求仍记录返回结果；恢复资金状态后继续，不清空已领取和待核对记录。

登录被明确拒绝、收到退出登录推送（包括其他设备登录）或停服推送时停止重连，记录原因，避免反复抢占账号。
`--stop` 能打断重连退避、连接和恢复等待。若仍在连通的牌桌，继续按优雅离桌流程退出；
已断线时直接收尾，不为退出而重新买入。

重连日志使用 `[RECONNECT]`；心跳超时同时记录距离最后收包的时间。自动重连无法还原断线期间
未收到的完整行动历史，现有恢复流程会禁用该手无法完整重放的 G5 旁路。

## 游戏服务自动绕过代理

启动命令无需设置 `NO_PROXY` 或 `no_proxy`。bot 恢复会话时，从登录响应中保存的
`servers[].server_host` 和 `servers[].http_host` 提取主机名/IP，去掉协议、端口和路径，
合并进当前进程的 `NO_PROXY` 与 `no_proxy`，保留用户已有条目。HTTP 地址为空时，
也加入该会话实际使用的默认 HTTP 主机。名单随登录返回的服务器列表变化，不写死游戏域名。

此步骤在选线 `/ping` 之前执行，覆盖全部备用线路的 WSS 和 HTTP 请求，包括自动领取奖励。
直接使用 `HeadlessSession` 建立连接时也会执行，重试时可补充更新后的地址。
不会修改系统代理设置、shell 配置或启动命令；macOS 的有效系统代理地址会保留到进程内，
避免新增 `no_proxy` 后其他地址意外失去代理配置。

`headless.log` 的 `[NETWORK]` 记录本次游戏服务名单，不记录凭证。
连接/登录失败及程序启动异常也写入该日志，即使控制台被重定向至 `/dev/null` 仍可排查。
更新代码不影响已运行进程，下一次启动生效。

## 对手历史数据查询

Headless 的 `/player/gameData` 使用当前会话的 HTTP 凭证、所选线路、渠道及客户端版本，
与游戏连接、奖励领取保持一致；不会回退到旧 `data/auth_token.txt`。
MITM 代理模式仍保留读取捕获 token 文件的方式。

- `code=-2` 按鉴权失败处理：记录并提醒一次，暂停使用同一凭证查询；有效凭证更新后可恢复。
- 只有 `code=0` 且明确返回 `play_times=0`，才提醒“暂无历史统计”，不据此判断新号、小号或激进倾向。
- 超时、请求失败和无效数据不记为“已查询”。冷却 30 秒后，在下一手开始时重试仍在本手的玩家，
  同一玩家的请求不并发重复，成功结果本次会话只取一次。
- 修改磁盘上的 headless 会话文件不会热更新已运行进程；新凭证由下次启动读取。

## 自动领取奖励

`python -m pf_intercept.headless` 默认领取发展基金、每日任务、每周任务、挑战任务和各自的活跃度宝箱。
本地及 VPS 的 Live 页在房间号上方显示本次启动累计的逐手净结算和已领取的奖励筹码。换桌、补买、锁仓和断线重连保留累计值。
原启动命令无需增加参数；临时关闭全部自动领取可追加 `--no-auto-rewards`。

### 蓝湾漫游

活动期间，bot 检查棋盘和任务，领取已完成任务的骰子，每次投一颗，并领取达到门槛的里程奖励。
德州任务沿用正常对局进度。每日可通过打开棋盘、在桌上给一名对手发送一次免费互动表情获得骰子。
彩球机和弹球机只做局数任务。bot 从服务器下发的可用档位中选最小注额，同价优先低档。
当前配置使用第 1 档，每局 1,000 筹码。单局上限 1,000 筹码，每种每天最多 24 局。
游戏日按 UTC+8 的 03:00 切换，用量记录在奖励日志里，重启后继续沿用。
本地和 VPS 的 Live 将棋盘和里程发放的筹码计入活动奖励，非筹码物品跳过。小游戏净输赢单独记账。

### 协会经营（派遣）

赛季内（客户端配置表：2026-08-27 10:00 至 2026-11-25 23:00，UTC+8），bot 每 5 分钟检查一次，在桌上打牌时也照常进行：

- **领奖**：事务到点后领取奖励（`/afk/recReward`）；随后领取已解锁的赛季通行证奖励（页面上的“一键领取”）、
  已完成的经营目标奖励，全部目标领完后领取赛季称号。有事务在进行时，bot 在最早结束的那一个到点后 5 秒被唤醒，不必等轮询。
- **派遣**：对列表里未派遣的事务，用**普通派遣**（消耗 1 瓶能量饮料）派出一名空闲牌手，每个事务派一人。
  事务按等级从高到低处理；牌手按客户端选人页的顺序选：同阵营优先（不减速、可出彩蛋），其次星级高，再次编号小。
  牌手星级不够、当日次数用完或正在派遣中的不选。
- **刷新**：所有已解锁事务所都没有可派遣的事务、而今天还有普通派遣次数、饮料和空闲牌手时，
  用一次**免费**刷新换一批事务，下一轮再派遣。
- 派遣数量以服务器返回的当日剩余普通派遣次数、背包里的能量饮料数和牌手当日剩余次数三者中最小的为准。

不做的事：不购买任何东西，不用强效能量饮料（高级派遣）、专注怀表（加速）和全新计划表（付费刷新），
不解锁也不升级事务所。事务所品质和要解锁哪个阵营由你在游戏里决定，bot 只用已经解锁的。

彩蛋、通行证和目标奖励里的筹码计入活动奖励；经验、好感度和道具只记日志。

失败处理：服务器明确拒绝的动作（返回错误码）6 小时内不再尝试，各动作分开计（列表、派遣、刷新、通行证、目标、
赛季称号，以及被拒的那一条事务奖励），记录为 `dispatch_blocked`，重启后仍然有效。
没有收到回复的请求不重发，下一轮先重新读取事务列表再决定。
另有本地上限：24 小时内最多发 18 次派遣请求、3 次刷新请求。

请求和配置表来自客户端 1.7.0 的 `DispatchModel.lua` 及 `tpl_*` 表，`tests/test_dispatch.py` 核对内置表与这些文件一致。
赛季时间写在代码里；换赛季或出新牌手、新服饰后需要按新客户端更新 `pf_intercept/headless/dispatch.py` 里的表。
只关闭这一项可追加 `--no-auto-dispatch`，其余奖励照常。

## 触发与领取流程

- 启动：WSS 登录成功并拿到首次钱包余额基线后，后台检查基金、每日、每周和挑战任务。
- 发展基金：收到 `pb.NoticeBRC.type=10082`（`GAME_REBATE_SETTLE`）立即唤醒检查。
  先查询 `/activity/rebateStatus`，有可领取状态才调用 `/activity/rebate`。
  后一个接口按客户端行为视为具有领取副作用，不能拿它当只读探测接口。
- 阶段切换：使用服务器时间，在 **UTC+8 的 07:00、19:00** 唤醒基金检查，
  跨阶段后的 10 分钟内每 30 秒复查；服务器仍在结算时也每 30 秒复查。
  日常每 5 分钟补查，覆盖断线、漏推送等情况；推送无需等待轮询周期。
- 任务：收到 `pb.NoticeBRC.type=10030`（`TASK_REFRESH`）合并短时间内的重复通知，刷新 `/task/list`。
  通知本身不代表任务已完成。仅领取列表中 `status=2` 的每日／每周／挑战任务，
  使用任务实例 `id`，不使用静态 `task_id`。
- 月卡专属任务：先读取 `/player/payInfo`，只在月卡有效期晚于服务器当前时间时领取。
  资格未知时跳过专属项，普通任务照常处理。
- 任务奖励：`/task/recReward` 指定符合条件的 `id_arr`，`all=false`，避免隐式领取未核验项目。
  随后刷新列表，再领取已达到门槛且未领取的 `/task/recPointReward` 活跃度奖励。
  每次领取后重新查询状态，允许本次任务奖励解锁的宝箱在同一次检查中领取。
- 协会经营：收到 `pb.NoticeBRC.type=10037`（`DISPATCH_TASK_REFRESH`）后重新读取经营目标。
  牌手和当前服饰来自对局连接上的 `pb.RoleListREQ`（每小时最多读一次），能量饮料数量来自 `pb.ItemListREQ`。

## 并发、失败和关闭

HTTP 调用在独立后台任务的线程中执行，不占用 WSS 接收循环、心跳或策略处理锁。
同一会话的领取请求串行处理，避免重复推送产生并发领取。
请求超时后不直接重发领取请求，下一轮先重新读取服务器状态。
这不能保证网络故障下的“恰好一次”：若服务器已发奖但响应丢失，到账金额可能无法确认，日志会标记 `claim_uncertain`。

某一项检查（基金、任务、蓝湾漫游、协会经营）失败后 30 秒重试；连续失败时间隔逐次加倍，最长 30 分钟，成功一次即恢复。
服务器推送到达时仍会立即检查，不受这个间隔影响。
棋盘和小游戏走对局连接，回复不带请求编号：某类请求超时后，同类请求暂停 60 秒等迟到的回复，之后视为丢失并恢复。

HTTP 返回 `code=-2` 表示鉴权失效，本次会话停止自动领取并记录提示，对局连接继续。
领取使用当前 WSS 会话对应的 `authorization`、渠道、客户端版本和线路 HTTP 地址，
不读取可能过期的独立 `auth_token.txt`，也不会自动登录并替换正在使用的账号会话。
更新本地会话凭证后，下次启动才使用新凭证。

关闭时停止新增领取请求，并等待正在执行的请求返回或超时，把领取结果记完再关闭。
测试使用模拟 HTTP/WSS，不会替账号领取真实奖励。

## 日志与资金看板

- 常规日志：`pf_intercept/logs/headless.log` 中的 `[REWARDS]`。
- 结构化记录：`pf_intercept/logs/rewards.jsonl`。
  包含时间、UID、本次奖励服务 `run_id`、事件、任务／宝箱 ID、奖励筹码及道具；不记录密码和 token。
  `claimed` 是收到成功响应，`claim_uncertain` 是领取结果无法确认，`auth_failed` 是鉴权失效。
  `check_failed` 是一次检查失败（服务器拒绝时带 `code`，程序异常时带 `error`）；
  `sidegame_skipped` 是当天没有符合上限的小游戏注额，写明原因后当天不再询问该游戏。
- 资金看板记三本互不相干的账，通知里的“本次启动盈亏”用的是第一本：
  - **本次对局盈亏**：服务端每手结算（`WinnerRSP.profit`）里自己那一项的累计，每手只记一次。
    它不看钱包余额，所以奖励到账、小游戏输赢、买入扣款的先后都不会影响它。
    （2026-11-06 至 11-14 的 156 段在桌记录里，这个累计与服务端离桌时给出的桌面盈利
    `LeaveRoomRSP.summary.profit` 除日志开头被截断的一段外全部相等，约 1.45 万手。）
  - **本次领取奖励筹码**：领取成功的奖励筹码。
  - **本次小游戏输赢**：为做活动任务玩的染色、弹珠小游戏的净输赢。
  钱包余额、桌上筹码、总筹码显示服务器实际值，只作展示。
- 某次领取或某局小游戏的结果无法确认时（日志 `claim_uncertain`），奖励和小游戏两项后面
  标注“另有待确认”；对局盈亏照常显示。

本功能不会启动 bot；代码更新在下一次启动时生效。

## 人机识别与选桌

**人机名单**（`pokerfate/data/local_models/robots.json`，本地运行数据，不入库）
由服务端下发的房内机器人数 `rb_num` 推出，不靠猜：

- 有人离桌（`OtherLeaveRoomBRC`）或进房（`OtherEnterRoomBRC`，服务端下发时）都会带上当时的 `rb_num`。
- 计数规则：房内还没判定的账号数正好等于 `rb_num` → 全是人机；`rb_num` 为 0 → 全是真人。
- 变化规则：两次计数之间 `rb_num` 的变化 = 进来的人机数 − 离开的人机数，
  即"这个人进来或离开时 `rb_num` 变没变"。
- 人数对不上（有人在房内但我们没看到）时这一次不推断。同一账号被判出两种结果时记为冲突，两边都不信。
- 证实的人机 UID 连成一段时（相邻间隔 ≤ 400、至少 5 个、段内证实真人不超过 2%），
  段内还没证实的账号按"疑似人机"处理，直到计数给出结论。

名单随对局自动增长并落盘。用历史流水重建或检查：

```bash
.venv/bin/python -m analysis.robot_wire            # 只看报告
.venv/bin/python -m analysis.robot_wire --write    # 用 headless.log 重建 robots.json
.venv/bin/python -m analysis.table_policy_dryrun   # 在历史流水上演练：每手开始时能否认出人机桌
```

**选桌**（`--bb` 进桌时始终生效，没有开关）只决定去留，打法不变。
记 H = 真人对手数，R = 人机数：

| 桌上情况 | 动作 |
| --- | --- |
| H = 0 且 R ≥ 1 | 立即离桌 |
| 空桌（刚进桌或打过牌后只剩自己） | 从桌子变空起等 60 秒，持续无人就换桌；期间有人进房就取消倒计时，按当前人数重新判断 |
| H ≥ 1 但 H < R | 还没发到牌：立即离桌；已在打：连续 2 手成立后离桌 |
| 其余 | 留下，照常打 |

- 进桌一律"等大盲再入局"，先看桌再决定，不白付盲注。
- 离桌后随机停 5–10 秒再匹配。
- 场次是**偏好顺序**，不是只降不升的阶梯：默认从 `--bb` 起由近到远、同距离先高后低
  （10000 → 20000 → 5000 → 2000 → 1000），用 `--stakes 10000,5000` 指定；
  只允许 1000 / 2000 / 5000 / 10000 / 20000，练习场是另一种游戏类型，不会进入。
- 找桌时总是先要"没在冷却的、最靠前的场次"。同一场次连续 3 张桌不合格算一轮失败，该场次进入冷却：
  第一次 15 分钟，之后逐次翻倍，最长 60 分钟；在该场次找到合格的桌就清零。
- **备选场次不会变成常驻**：在靠后的场次打牌时，只要有更靠前的场次冷却结束，
  打完当前手就离桌回探——一次把已到期（或 10 分钟内到期）的更优场次都探完，每个场次试 2 张桌；
  都不行就直接回到刚才能打的场次，下次回探的间隔翻倍。
- 离开一张已经打过牌的桌子时发一条通知（标题写原因，正文是本次启动盈亏），因为下一张桌会重新买入、
  桌上筹码不再连续；刚进桌一看不合格就走的不发。
- 每个可用场次都连续失败 3 轮后停在大厅并发通知，重启后恢复。
- 服务器拒绝某个场次的匹配（筹码或等级不够）时，本次运行不再尝试该场次。
- 盈利锁仓、破产换桌、异常离桌重进照旧；它们进行中时选桌不插手。
- 每次进桌、离桌、匹配都追加一行到 `pf_intercept/logs/table_select.jsonl`
  （时间、房间、盲注、真人数、人机数、依据、各座位的判定）。

参数默认值在 `pf_intercept/config/__init__.py` 的 `TABLE_SELECT_*`。

**学习与选桌用同一条判断。** 桥接层把每手里的人机标给策略层（策略日志 `hand_start.players[].robot`，
中途接入的牌局同样标记）。策略照常决策，学什么按发牌名单套选桌规则（`table_verdict`）：

- **需要离桌的牌局**（没有真人，或真人少于人机）：整手不参与任何学习和采集——不记校准预测和训练行，
  不记河牌价值尺度和范围对照样本，不更新 G5 画像，不更新任何账号的统计。
- **留桌的牌局**（真人不少于人机）：真人照常记录；人机自己不记训练行、不进 G5 画像；
  只要还有人机没弃牌，这一刻的预测不作为 hero 胜率自校准的样本，也不记河牌价值尺度样本。
- 没有人机的牌局一切照常。

回放提取训练行时按同一规则处理。离线训练脚本（`fit_range_lgbm_calibration`、
`build_range_v2_empirical_model`）一律按名单剔除人机行，没有开关。规则生效之前写下的旧数据用
`python -m analysis.robot_relearn calibrator --apply` 和 `rows --apply` 清理（先前者后后者，bot 停止时执行，
原文件留有备份）。
CFR 对手先验（`pokerfate/decision/opponent_numeric_prior.py`）启动时从 `opponents.json` 建
"对手池基准 + 相似玩家库"，人机不进这个库；`opponents.json` 里人机自己的记录保留，
真遇到这个账号时仍用它自己的数据。

选桌、人机识别（名单增长）和"人机不进学习"都没有开关，始终生效。
